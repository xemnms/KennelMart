================================================================================

ON SCREEN
- Unverified sellers
- No campus-specific marketplace
- No structured transaction flow

FULL SCRIPT
"Before building any system, we defined the real user problem.

Students frequently buy and sell second-hand items such as uniforms,
textbooks, gadgets, and services. But today, most of these transactions happen
in Facebook groups or random group chats.

The first issue is trust. There is no verified identity check, so buyers can
easily be scammed.

The second issue is context. Existing marketplaces are public and not tied to
NU Laguna, so users cannot confidently know they are transacting within the
campus community.

The third issue is process. Informal chat-based selling has no order tracking,
no status history, and no consistent payment or meetup flow.

The fourth issue is accountability. If something goes wrong, there is no formal
reporting and no admin workflow to review violations.

So our formal problem statement is this:
NU Laguna students and faculty need a safe, verified, and structured platform
for campus-based buy-and-sell transactions.

KennelMart was built to directly answer that need."

Router for navigation, Zustand for state management, and Axios for API calls.

In terms of user features, KennelMart supports the complete commerce cycle:
browsing listings, searching and filtering, adding items to cart, multi-seller
checkout, order status tracking, direct messaging, notifications, and post-sale
reviews.

For governance and safety, we include reporting features and a dedicated admin

In short, we transformed an informal and risky process into a structured,

SLIDE 5 - SYSTEM ARCHITECTURE AND FEATURE TOUR (2:00)
================================================================================

ON SCREEN
- Layered architecture:
  HTTP -> Controller -> Service -> Repository -> Database
- Domains:
  auth -> user -> verification -> listings -> cart -> orders -> messages ->
  notifications -> reviews -> reports -> analytics

FULL SCRIPT
"Our backend uses a clean layered architecture.

At the top, controllers receive HTTP requests, validate inputs, and return
responses.

Controllers do not contain business logic. They delegate to services.

The service layer contains all business rules, validation logic, cross-entity
orchestration, and workflow decisions.

Services then call repositories, which isolate database access using JPA query
methods and JPQL where needed.

Repositories interact with PostgreSQL, where our entities are stored as
relational tables.

This architecture gives us clean separation of concerns. Every layer has one
job, and each layer is easier to maintain and test.

Feature-wise, the system is organized into connected domains, from auth and
user verification all the way to orders, messaging, reviews, reports, and
analytics."

SLIDE 6 - OOP CONCEPTS APPLIED (4:00)
================================================================================

ON SCREEN
- Abstraction
- Encapsulation
- Inheritance
- Polymorphism

FULL SCRIPT
"In this project, we intentionally applied all four OOP pillars.

First is abstraction.
We use an abstract BaseEntity and multiple service interfaces. BaseEntity
defines common fields like id, createdAt, and updatedAt. Service interfaces
define what operations are available, while hiding implementation details.
Controllers only depend on interfaces, not concrete classes.

Second is encapsulation.
Our entities and DTOs keep fields private and expose controlled access through
methods. For example, user password handling is never exposed directly; it is
processed through secure service logic. This protects internal state and avoids
invalid object mutation.

Third is inheritance.
All core entities inherit from BaseEntity. This avoids repeating boilerplate
for identifiers and timestamps in every class. If we need to evolve shared
fields later, we do it once in the parent class.

Fourth is polymorphism.
Service interfaces are implemented by concrete classes and injected by Spring at
runtime. A controller can call OrderService without knowing whether the
underlying implementation changes. This keeps modules decoupled and supports
future extension.

So these are not just textbook definitions. They are visible in our daily code
structure, dependency boundaries, and runtime behavior."

SLIDE 7 - OOP BEST PRACTICES AND DESIGN PATTERNS (3:30)
================================================================================

ON SCREEN
- Builder Pattern
- Repository Pattern
- DTO Pattern
- Service Layer Pattern
- SRP, OCP, and DI/IoC

FULL SCRIPT
"Beyond the four pillars, we used practical OOP-friendly patterns.

First, Builder Pattern.
Our response DTOs often contain many fields, so we use builders for readable,
order-safe object construction. This improves clarity and reduces constructor
errors.

Second, Repository Pattern.
Data access is isolated in repository interfaces extending JpaRepository.
Business logic stays in services, while repositories focus on persistence and
queries.

Third, DTO Pattern.
We never expose entities directly to the API. Request DTOs validate inputs at
the boundary, and response DTOs expose only safe, necessary fields.

Fourth, Service Layer Pattern.
Controllers do HTTP concerns only. Services own business workflows. This keeps
the API layer thin and the domain layer cohesive.

We also enforce SOLID principles:
- SRP: each class has one clear responsibility.
- OCP: modules are extendable through interfaces without breaking callers.
- DI/IoC: constructor injection makes dependencies explicit and testable.

As a result, our codebase remains organized even as features grow."

OPTIONAL Q&A BANK (USE IF ASKED)
================================================================================

Q1: Why did you choose Java Spring Boot?
A: We chose Spring Boot for strong enterprise patterns, built-in dependency
injection, mature security libraries, and clean layering support for OOP.

Q2: How is security handled?
A: We use JWT bearer authentication, BCrypt password hashing, role-based
authorization, and restricted institutional email registration.

Q3: Why use DTOs instead of exposing entities?
A: DTOs prevent overexposing internal fields, enforce API contracts, and keep
controller-level validation clean.

Q4: What can you improve next?
A: We can add payment gateway integration, cloud file storage, stronger audit
logs, and push notifications.
